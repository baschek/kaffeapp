# Kaffee sync contract v1 (TESS server ↔ Android app ↔ website)

Binding for all three sides. Server = TESS on the Pi (`/kaffee/v1/*`, base URL = `TESS_PUBLIC_URL`). Clients: the native
Android app (repo `kaffeapp`, folder `android/`) and the website (same repo, React PWA on GitHub Pages,
`https://baschek.github.io/kaffeapp/`). JSON, UTF-8. Events are exactly the coffee app's `InventoryEvent` objects
(camelCase, see `kaffeapp/src/types.ts`); everything else is snake_case. Timestamps ISO-8601 UTC with `Z`.

The journal is the only data: clients keep a local copy plus an outbox of events they created, push the outbox and
pull new events. The stock is always derived locally with the shared rules (golden cases:
`TESS/tests/fixtures/coffee_golden.json`, generated by `kaffeapp/src/golden/golden.test.ts`).

## Data endpoints (both credential types)

| Call | Response |
|---|---|
| `GET /kaffee/v1/status` | `{ "seq": N, "events": count, "server_time": ts }` |
| `GET /kaffee/v1/snapshot` | `{ "seq": N, "document": {schemaVersion:1, createdAt, settings, events[]}, "bean_links": {package_id: bean_document_id} }` (events in server order) |
| `GET /kaffee/v1/events?since=<seq>&limit=<1..500, default 500>` | `{ "events": [ {"seq": n, "origin": "app"\|"web"\|"claude"\|"import"\|"drive", "event": {...}} ], "next_since": M, "has_more": bool }` ascending by seq |
| `POST /kaffee/v1/push` body `{ "events": [event, ...] }` (max 200 events, max 2 MB) | `{ "results": [ {"event_id", "status": "applied"\|"duplicate"\|"rejected", "reason": "<German text, rejected only>"} ], "seq": N }` |

Push rules: an event must have an id (≤100 chars), a known `type`, `recordedAt`/`effectiveAt` with a time zone and at
most 5 minutes in the future, `resourceIds` (list of strings) and `data` (object); otherwise it is rejected with a
reason. Events are processed in the given order, each one exactly like a booking by Claude: it is stored only if it
creates no new derivation warning on the server's current journal (`coffee.append`). `duplicate` = the id is already
stored (idempotent replay; the stored version wins). A rejected event is NOT stored; the client removes it from its
outbox, drops it from its local journal and shows the reason ("Buchung abgelehnt: …"); events of the same push that
depend on it are rejected too. The client keeps `recordedAt`/`effectiveAt` as created on the device. Origin is `app`
for the Android credential and `web` for a passkey session.

Client sync algorithm: (1) push the outbox in creation order, (2) pull `events` since the stored cursor until
`has_more=false`, (3) first run, unknown cursor or `410 {"error":"resync_required"}` → `snapshot` and replace the local
journal (outbox events not yet acknowledged stay and are pushed again). Triggers: app start, after every booking,
periodic (Android WorkManager ~15 min, network required; website on focus), manual button. Show
`last_successful_sync_at`.

## Credential A: Android device (same hardening as gym amendment B, own device slot)

- `./tessctl kaffee-pair [--replace]` prints a one-time code (≥10 chars, unambiguous alphabet, 10 min, single use);
  `./tessctl kaffee-devices`, `./tessctl kaffee-revoke <id>`. At most ONE active Android device.
- `POST /kaffee/v1/pair` `{ "code", "device_name", "public_key" }` (EC P-256 SPKI, base64url, generated in Android
  Keystore, non-exportable, StrongBox if available) → `{ "token", "device_id" }`. Exists only while a code is open.
- Every call: `Authorization: Bearer <token>`, `X-Kaffee-Timestamp` (unix seconds, ±300 s), `X-Kaffee-Nonce`
  (16+ random bytes base64url, single use within 10 min), `X-Kaffee-Signature` (base64url DER ECDSA-P256-SHA256 over
  `METHOD\nPATH\nQUERY\nTIMESTAMP\nNONCE\nSHA256_HEX(body)`, PATH without host, QUERY raw or empty).
- 120 days without a successful request = expired (re-pair).

## Credential B: website with a passkey (WebAuthn)

- Relying party: `rp.id` = `TESS_KAFFEE_WEB_RP_ID` (default `baschek.github.io`), allowed origins
  `TESS_KAFFEE_WEB_ORIGINS` (comma separated, default `https://baschek.github.io`; add `http://localhost:5173` for
  development). ES256 (-7) required, RS256 (-257) accepted; attestation `none`; `userVerification: "required"`;
  discoverable credential (`residentKey: "required"`). Several passkeys allowed (phone, laptop).
- Adding a passkey needs a one-time code from the Pi: `./tessctl kaffee-passkey-code` (10 min, single use).
  `./tessctl kaffee-passkeys` lists them (label, created, last used), `./tessctl kaffee-passkey-revoke <id>`.
- `POST /kaffee/v1/webauthn/register/options` `{ "code" }` → `{ "ceremony_id", "options": <PublicKeyCredentialCreationOptionsJSON> }`
  (wrong/expired code → neutral 404)
- `POST /kaffee/v1/webauthn/register/verify` `{ "ceremony_id", "credential": <RegistrationResponseJSON>, "label" }` → `{ "ok": true, "passkey_id" }`
- `POST /kaffee/v1/webauthn/login/options` `{}` → `{ "ceremony_id", "options": <PublicKeyCredentialRequestOptionsJSON> }` (empty allowCredentials)
- `POST /kaffee/v1/webauthn/login/verify` `{ "ceremony_id", "credential": <AuthenticationResponseJSON> }` → `{ "token", "expires_at" }`
  (session 12 h, opaque, only its hash stored; sign counter checked when the authenticator provides one)
- `POST /kaffee/v1/webauthn/logout` (Bearer) → `{ "ok": true }`
- Data calls: `Authorization: Bearer <session token>`. The website keeps the token in `sessionStorage` only.
  Ceremonies expire after 5 min and are single use. JSON shapes follow WebAuthn Level 3 `toJSON()` (base64url fields),
  so the browser side can use `PublicKeyCredential.parseCreationOptionsFromJSON` / `parseRequestOptionsFromJSON` with a
  small fallback.
- CORS: only for the allowed origins on `/kaffee/v1/*` (incl. preflight): `Access-Control-Allow-Origin: <origin>`,
  `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type`,
  `Vary: Origin`, never `Access-Control-Allow-Credentials` (the website calls with `credentials: "omit"`). The neutral
  404 carries these headers too when the request comes from an allowed origin, so the website can read it and treat
  an authenticated 401/404 as "session expired, log in again" (and a network error as "Pi unreachable").
- A passkey for `rp.id` `baschek.github.io` can be used by every page under `https://baschek.github.io/` (e.g. the
  old GymApp PWA). That is acceptable because all those pages are Jonathan's own code, but no third-party code may
  ever be published there.

## Errors and fingerprinting

Like gym amendment B: every unauthenticated or invalid request to `/kaffee/v1/*` gets the server's generic 404 (same
body as an unknown path), with deliberate exceptions that must exist publicly for the website:
`webauthn/login/options` and `webauthn/login/verify` (verify still answers a failed login with the neutral 404), and
the CORS preflight (`OPTIONS`) for an allowed origin. These reveal that the coffee API exists; the data stays behind a
credential. The Android pair endpoint exists only while a code is open, `webauthn/register/options` answers only with
a valid code (both neutral 404 otherwise).
Both are rate limited; floods trigger the same temporary global lockout as gym. 429 only for an authenticated client
over its rate limit. Details only in the server log, never secrets.

## Drive backup (server only)

The sync worker writes the journal every night into the existing `Kaffee-Bestand/kaffee-bestand.json` in Jonathan's
Drive (file id `TESS_KAFFEE_DRIVE_FILE_ID`, shared with the TESS service account as editor), in exactly the coffee
app's file format, plus optionally `bestand-aktuell.csv` (`TESS_KAFFEE_DRIVE_CSV_ID`, a file Jonathan created and
shared; a service account cannot create files in his Drive). Before writing it reads the file and takes over events
that only exist there (written by the old web app in an emergency) with origin `drive`, validated like a push;
rejected ones are reported on the status board and never block the backup. `./tessctl kaffee-backup` runs it now.
